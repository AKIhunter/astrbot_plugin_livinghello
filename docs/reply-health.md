# 回复闭环与管理员提醒

启用入口：LivingHello 控制台 → 回复与私聊 → 断线恢复。

## 错误分类与处置

所有回复链路的错误先经过 `guard_reply_health.py` 的 `classify(value)`，返回
`(category, disposition)`。`category` 用于页面、日志和提醒文案；
`disposition` 只有四个值，各层按它决定动作，不再逐个状态码写分支：

| disposition | 判定来源 | 处理 |
| --- | --- | --- |
| `retry_then_rotate` | 空响应、协议错误、超时、连接错误、HTTP 408/429/5xx | 原地重试一次，仍失败换候选 |
| `rotate_now_report` | 配额耗尽、认证失败、配置错误 | 立即换候选并记录 |
| `not_an_error` | 撤回、上下文过期、策略取消、主动静默 | 不重试、不告警，按主动静默收尾 |
| `fail_report` | 无可用上游、模型缺失、投递/收尾类失败 | 直接记录并上报 |

判定顺序固定：先识别已归一化的类别与预期静默原因，再匹配配额关键字，最后才看 HTTP 状态码。
这样才能避免 403/429 同时可能是欠费时被误当成普通限流。`DISPOSITION_BY_CATEGORY`
是类别到处置的唯一映射表，新增类别必须同时补表。

## 异常锚点 `[ReplyFault]`

无法归类、但需要留下证据的异常会打一条单行 WARNING，字段为
`code`、`stage`、`category`、`disposition`，有请求 ID 时追加 `request_id`。
当前共 3 个调用点、3 个场景码：

| 场景码 | 触发条件 | 目的 |
| --- | --- | --- |
| `ALARM_STALE_SUMMARY` | 本轮已投递成功，但 summary 仍是 `failed`（本轮内先失败后成功） | 说明告警已按失败发出，成功分支不覆盖 |
| `INTENTIONAL_COERCED_FAILED` | 预期静默类别没有被 `finish` 拦截，即将被改判为 `model_reply_missing` | 暴露静默判定与失败收尾的边界错位 |
| `CONTEXT_CHANGED_TYPEERROR` | `cancel(context_changed)` 缺少 `_at_guard_judged_revision`，下一行会抛 `TypeError` | 标记旧闸门兼容路径，保留原异常行为 |

锚点只增加诊断信息，不改变分类结果、重试次数或投递行为。

## 水位顶替

水位从消息到达时刻（`_at_guard_received_at`）起算，不按租约、也不按主模型开始时间。
`private_watermark_window_seconds`（默认 15 秒）内同一会话又收到新消息时：

- 尚未发送的旧回复被顶替，发送前复核按 `superseded_by_new_message` 丢弃正文。
- 分段发送中的旧回复停止剩余气泡；已经发出的不回收、不回滚。
- 窗口外到达的新消息不顶替旧回复，旧回复照常发送，新消息按自己的轮次生成。
- `0` 关闭水位顶替，旧回复一律发送。
- `watermark_scope=private`（默认）只作用于私聊；设为 `all` 时同一个窗口也用于群聊。
- 300 秒回复机会有效期优先级高于水位，超期一律按 `message_expired` 丢弃。

本轮不调用 `request_agent_stop_all`：只丢弃发送并阻止被顶替事件后续的视觉批次，
已完成批次的图片摘要保留。

已知限制：

- 旧回复被丢弃后，宿主已写入历史的 assistant 文本无法安全移除；新请求可能仍看到它。
- 宿主的 follow-up 捕获可能把新消息并入旧 run 的工具结果并丢失图片；本层不拦截捕获。

## 状态与不变量

| 规则 | 代码位置 | 检验 |
| --- | --- | --- |
| 成功必须有模型完成、正式包投递成功、流程结束三项证据 | `ReplyHealth.finish`、`ReplyDelivery.patch` | 主备失败、错误提示、末包缺失与分段部分失败 |
| 工具提示或错误文本不能被当作正式回复 | `ReplyHealth.arm` 的事件局部身份标记 | 直接发送、派生媒体、流式生成 |
| 所有故障层共享600秒提醒额度，重载和并发不增加额度 | `ReminderStore.claim` 的 SQLite 原子事务 | 并发、599/600秒边界、重载、认领后崩溃、时钟倒退 |
| @ 的目标仅来自显式管理员 QQ 或全局管理员的有效 QQ | `ReplyHealth.admins`、`notify` | 普通用户、全体成员、非QQ平台与非法号码 |
| 正常门控静默、撤回和名单取消不报断线 | `ReplyHealth.finish` | 规则取消与故障反例 |
| 已放行流程最终没有回复，应在流程结束或最长等待后记录并尝试提醒 | pipeline 完成回调、watchdog | 原生宿主任务结束、挂起、缺失回调 |

每个事件有独立状态：准备 → 等待模型 → 等待最终发送 → 完成 / 未确认。真实宿主为每条消息创建独立的 `PipelineScheduler.execute` 任务，完成回调负责终结判定，避免被宿主吞掉的异常留下“运行中”。兼容未知宿主时采用有界等待；默认900秒，允许60–7200秒，不取消真实模型任务。

观察模式中的判定故障如果最终主模型成功投递，不发断线提醒。流式生成必须完整耗尽后才发送正式内容；中途超时不将半截输出记作成功。只有 @ 或引用而无正文也不是正式回复。

## 提醒路由与未知结果

“提醒管理员 QQ”可填最多20个有效 QQ 号；留空时使用全局 `admins_id` 中有效 QQ 号。配置该项表示指定这些账号接收管理员提醒，不修改宿主权限。缺少号码时仍记录故障，并在页面显示“缺少管理员 QQ”。

群聊故障在原群发一条消息，原生 @ 仅包含管理员；私聊故障发往管理员私聊。固定文案不包含技术错误、用户正文、提示词或凭据，且不经过自动引用或 @ 当前发言者的表达规则。QQ 号不能转换为其他平台账号。

在发送前先持久化认领全局提醒额度。发送超时或返回失败后结果记为未知；不释放额度，不自动重试。600秒后再次出现故障可获取下一轮额度。恢复只更新状态，没有额外恢复提醒。

`event.send` 正常返回 `None` 是宿主的标准成功契约；显式 `False`、失败状态或非零 `retcode` 不能作为投递成功。宿主的“发送后”回调不能单独证明发送成功。平台投递证据不等于用户已读。

## 数据与验证边界

提醒数据库只保存最近状态的固定故障类别、层级、时间和全局额度时间，不保存正文或目标账号。存储不可用时停止外发提醒，以免重载后重复 @；页面显示存储异常。

验证使用隔离事件、受控发送回执、原生宿主任务和固定种子 `20261106`，不调用真实模型，不向群或管理员发测试消息。强制杀进程、整机断网或发送平台不可用时无法保证提醒到达；未确认结果必须保留为未知，不能声称通知成功。
