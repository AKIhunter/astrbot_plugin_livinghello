# 碎片消息等待与合并判断

在「guard → 回复节奏」设置：

| 参数 | 默认值 | 行为 |
| --- | --- | --- |
| `fragment_wait_seconds` | `3` 秒 | 同一用户续发时重新计满此秒数；0 关闭等待 |
| `fragment_max_wait_seconds` | `10` 秒 | 从该批第一条消息起算的总等待上限；0 不限制 |
| `fragment_wait_private` | `false` | 私聊是否也等待并合并连续输入 |
| `apply_to_private` | `false` | 私聊是否执行参与判断，与碎片等待独立 |

群聊普通消息、明确 @、引用机器人和称呼唤醒都会等待。只在完整会话中，同一用户的
续发会重置倒计时；其他用户、其他群、其他平台或私聊不会重置，也不会被收进这一批。

例如：第 0 秒 @ 机器人，第 2 秒发送「我想问」，第 4 秒发送「怎么加点」。
第 7 秒安静期结束，一起判断这三条输入，只保留最后一条作为回复触发。
连续续发会继续重置，不会每隔 3 秒插一次话。

## 总等待上限

`fragment_max_wait_seconds` 约束整批的最长等待时间，从该批第一条消息到达时刻开始算。
每次续发只把静默计时重置为 `fragment_wait_seconds`，不会延长总上限；两者取更早的时刻结束等待：

```text
batch_deadline = min(now + fragment_wait_seconds, first_seen + fragment_max_wait_seconds)
```

因此用户可以持续续发，但整批不会无限延长。到点即使用户仍在输入，也用当前已合并内容进入判断。
`0` 表示不限制，此时续发可以无限延长整批，回复更容易在发送前超过有效期而被判过期。

控制台会在两个值不匹配时给出联动警告：`gate_reply_max_age_seconds` 小于
「静默等待 + 总上限 + 40 秒」时提示整批回复可能在发送前过期。该警告只提示，不阻止保存，
也不会改写已保存的配置。碎片等待关闭（`fragment_wait_seconds=0`）时不产生该警告。

## 判断与回复

开启等待时，明确呼叫免主动回复冷却，但也需要对完整输入做一次参与判断。
后续补充「不用回了」等结束意图可以使整批静默；判定失败、预算不足等沿用原闸门规则。
关闭等待时明确呼叫沿用直接放行行为。

整批仍只有空 @ 时，安静期结束后才发送固定文案或发起当前人格的简短回应。
空 @ 后补了问题或图片，则按完整输入正常判断，不会先发送「嗯？」。

开启私聊等待、关闭私聊过滤时：连续私聊会合并交给主模型，不新增参与评分。
同时开启私聊过滤时：安静期结束后也执行原参与判断。
群聊参与判断设为 off 时群聊不聚合；已开启的私聊等待仍能独立工作。

## 代码顺序

`guard_fragments.py` 管理短期 `Batch` 和每条消息的 `Ticket`，以
`(unified_msg_origin, sender_id)` 分批，用单调时钟计算最后到达后的安静期。
`Batch.started` 记录首条消息时刻，`Batch.max_wait` 记录总上限；
每次续发用 `min(now + 静默秒数, started + max_wait)` 重算 `deadline`，`max_wait<=0` 时只取安静期。
不依赖判定模型、归档或撤回窗口结束时间计算续发间隔。

`main.py` 的事件顺序如下：

1. `observe_message_fragments`（`maxsize + 30`）：立即记录到达和原始文本、
   @、引用与图片信息；同批曾明确呼叫时，让无 @ 的后续消息继承唤醒资格。
2. 原有撤回保护（`maxsize + 20`）与群聊规则（`maxsize`）。
3. 从绫原消息归档（当前配套版本 `maxsize - 101`）：逐条保留原文和原组件。
4. `coalesce_message_fragments`（`maxsize - 110`）：旧触发停止，最后一条等待安静期，
   完成后认领这一批；随后才进入从绫作息、爬楼和模型流程。
5. `guard_llm_request`：合并文本供判断，完整分片列表作为判定元数据和回复模型的
   临时输入。保留宿主原始 prompt 和消息组件；较早分片的图片也能传递。

等待期间其他人的消息可由原上下文机制提供背景，但不属于同一用户的合并输入。
整批只产生一次参与判断流程；需要图片或记忆时，该流程仍可沿用原有多阶段调用。

原有从绫准备计时、正文有效期和新消息撤销继续生效。新消息到达即使旧快照过时，
不等待其撤回窗口或归档结束。开启撤回保护时，本批任何一条原消息撤回，都会取消
尚未发送的整批回复；原始归档按原有撤回窗口规则处理，不额外删除历史记录。

## 边界与配置

- 插件重载取消待处理等待；短期分片不持久化，不会重载后自动重放。
- 同会话、同平台消息 ID 的重复投递不重置倒计时，120 秒内保留有界去重索引。
- 撤回/其他通知及机器人自身消息不加入分片，也不重置倒计时。
- 缺少发送者或完整会话标识时，不启用聚合。
- 最多 256 个活动会话用户批次；每批最多 128 条、文本合计 65,536 字符。
  超限批次静默，不截断后判断，原消息仍逐条归档；安静期结束后可接受新批次。
- 已保存的等待秒数继续生效；新默认值为 3 秒，不自动覆盖用户此前手动保存的配置。
- `fragment_max_wait_seconds` 新默认为 10 秒；旧配置没有该键时按默认值生效，不需要迁移。
- 总上限只限制批次等待，不改变判定、生成或回复有效期；三者各自独立计算。
