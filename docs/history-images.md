# 历史图片的输入优化

LivingHello 负责图片理解，MultiApiRouter 在发送上游前压缩历史图片副本。原生对话历史仍保留原图，当前图片和明确引用的图片继续按现有流程理解。

## 每次请求如何处理

1. 当前用户的图片及本轮工具输出图片保留。
2. 最近两个历史用户轮次内最多保留四张原图。
3. 其他旧图改成文字占位，保留本条及后续已存在的图片观察文字，并复用原生历史中保存的逐图补读结果。
4. 没有逐图摘要时明确说明不能猜测画面，不把多图整体观察擅自分配给单张图。

LivingHello 将本轮已经成功得到的图片整体观察交给原生历史保存。不主动重看旧历史，不增加独立图片数据库。原图、摘要、checkpoint 的保存与删除继续受原生历史生命周期控制。

## 需要旧图细节时

主模型可调用 `livinghello_read_history_image`，只接受本次事件已授权历史中的图片标识，不能指定 URL、会话或用户 ID。一次请求最多补读一张，最多等待十二秒，生成上限 1,024 Token，保留结果最多二千字符；失败、超时或取消后不重试。

使用“特殊消息理解”的图片 Provider，传入 `request_max_retries=0`。如果该 Provider 本身是路由，其现有上游尝试策略仍适用，十二秒外层期限会取消本次调用。无可用模型时返回未识别。

本次历史最多登记三十二张可补读图片，重复引用共用标识。名单改变、事件变化、授权失效或撤回后停止补读。群历史缺少逐图作者，启用黑名单时不提供旧图补读工具；当前明确引用图片仍走既有作者校验流程。

## 预算与保存安全

默认文字预算 262,144 字符，内联/本地图片单张 8 MiB、合计 32 MiB，实际发送最多 32 张。这不是模型 Token 或图片能力上限。远程 URL 不额外下载计量，限制地址长度和数量，实际下载体积由上游约束。

压缩仅发生在路由的发送副本，不修改 `ProviderRequest.contexts`、runner 消息或数据库。原生 Message 的 checkpoint/no_save 私有属性保留。下一次原生历史保存仍包含旧图。

旧历史缺失的摘要不能凭空恢复。补读会产生一次逻辑视觉调用的用量；用户回复只表达核对结果，不应输出内部标识、编码或工具机制。
