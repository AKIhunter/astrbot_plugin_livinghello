# LivingHello 插件

用于 AstrBot 4.29.1 及以上版本。

当前控制台为运行概览、判定设置、回复与私聊三页，最近判定已合并到概览。
回复方式仅保留确定性引用、@和Emoji/颜文字清理；分段共用AstrBot原生配置。
可独立使用，也可接入 LivingMemory / LivingEmotion；从绫兼容保留感知与固定人格，动态功能由统一耦合控制。完整分支见 [HTML 图解](flow/index.html)，接入差异见 [四种组合说明](integrations-and-flow.md)。
新增配置、代码交接及迁移详见[回复方式与原生分段](expression-takeover.md)。

## 快速使用

1. 打开插件详情页的 `guard` 控制台，日常模式选「硬闸门」。
2. 在「参与判断」设置文字小模型和参与阈值；例如阈值50表示分数至少50，
   还必须理解上下文并且没有静默否决，才有机会放行。
3. 需要处理图片时，在「图片与主模型兜底」选择支持图片的模型；
   只有看图模型调用异常时，才尝试开启的会话主模型兜底。
4. 每项参数下面直接显示用途与例子。右侧或下方配置区可调预算、上下文、
   回复节奏、称呼及私聊；例子只是说明，不会自动应用。
5. 点击「保存参数」或底部「保存更新」。可在下方「文字试跑」验证结果，
   它不发群消息、不计插件预算，但会产生模型API用量。

面板分为运行概览、判定设置、回复与私聊、最近判定四页；切页保留草稿。
参数仍按参与判断、图片与主模型兜底、上下文与记忆、预算时限、回复节奏、称呼私聊分组，窄屏改为单列。
普通保存不清零记录；调整前三个判定板块时保存栏额外提示口径变化。最近判定支持群ID/私聊QQ搜索与能力耗时详情，见[记录与计时说明](console-records.md)。
每个配置标题右侧有 `?` 详情按钮，点击后显示完整解释和两个独立示例，减少页面常驻说明。顶部「参数手册」仍支持搜索参数名、字段名、用途和示例，并复用同一份定义。

多数参数保存后立即生效；称呼的框架唤醒前缀在插件启动时注册，
修改称呼后建议重载插件。固定文案、人格要求和兜底超时只在对应模式开启时可编辑。

## 痛点

AstrBot 在群里默认会「主动回复」——但它并不知道一句话是不是真的该接。结果通常是两种：

1. **乱插嘴**：群友之间闲聊、别人在对话、或者一句没头没尾的碎片消息，机器人也凑上去回复，
   显得很没边界感，甚至招人烦。
2. **烧钱**：每条「不该回」的消息，主模型都完整生成了一遍再被丢掉。实测旧行为下，
   被静默的消息每条都完整生成过一遍，约占 ¥2.6/天、全站 17% 的生成开销。

本插件做的事：在**主模型生成之前**，用一个小模型快速判断「这句话值不值得我接」，
不值的直接拦下——既不刷屏，也不花主模型那份钱。

几个关键取舍：

- **小模型只做「判断」，不做「生成」**：判定模型只输出一行 JSON（该不该接、参与适合度、是否理解背景、原因），
  不负责写回复内容。判断和生成彻底分开，省下的是生成侧的钱。
- **宁可不回，也不乱回（fail-closed）**：判定超时、输出解析失败、分数不足，一律静默。
  放过一条无关消息会在群里刷屏，漏掉一条则只是少说一句，代价完全不对等。
- **规则层零成本前置**：最短字数、纯表情、每小时预算、去重、冷却这些不需要模型的，
  先用规则拦掉，模型只处理真正需要语义判断的那部分。

## 功能

- 闸门式判定：小模型输出 `act/conf/understood/reason/ground`；背景不足、互聊、结束话题或低分在**主模型生成之前**拦住。
- 两种模式可切换：`enforce` 按判断拦截 / `shadow` 只观察；旧 `legacy` / `off` 归一到 `enforce`。
- 内置控制台（插件详情页 → guard）：改阈值、换判定模型、试跑、看最近判定与今日统计。
- 判定留痕：`decisions.jsonl` 记录分数、结论、原因、耗时、模型原话，可直接拿来校准阈值。
- 零成本规则层：最短字数、全表情、每小时判定预算、去重、冷却。
- 硬过滤只 @ 其他用户、没有 @ 机器人的消息。
- 仅 @ 机器人且没有正文时，可选择固定文案或按当前 AstrBot 人格生成回复。
- 支持 AstrBot 多人格：人格回复不绑定固定人格 ID，各会话会沿用自己当前选择的人格。
- 可选择是否对私聊启用参与过滤，默认关闭；私聊碎片等待、表达与撤回使用独立开关。
- 支持机器人昵称唤醒、碎片等待、主动参与冷却和重复消息去重。

## 行为

- 仅 @ 其他用户、未 @ 机器人：在调用模型前硬拦截，不发送回复。
- 同时 @ 其他用户和机器人：正常处理。
- 原生 @ 当前机器人：保留碎片等待，合并后直接进入主回复，不被参与小模型误判成互聊。
- 无 @ 普通群消息：由 `proactive_group_judge` 控制。默认 `whitelist_empty` 在群白名单为空时也补一次判定，`all` 不依赖白名单是否为空（白名单内的群也补判定，名单外群仍只读静默；黑名单、灰名单除外），`off` 恢复为只沿用 AstrBot 主动回复策略；开启后每个群消息都会跑一次判定模型，成本随群消息量上升。判定仍结合近期群聊流水严格判断是否真正理解话题，静默时不生成回复。
- 碎片等待结束后，整批仍仅 @ 机器人且无具体内容：
  - `fixed`：直接发送配置中的固定文案，不调用模型。
  - `persona`：调用当前会话的模型，按该会话已选择的 AstrBot 人格生成一句简短自然回应。
- 以「助手」或「bot」开头：视为明确唤醒，不受主动回复概率限制。
- 引用机器人消息：沿用 AstrBot 自带的引用唤醒行为。
- 普通群消息由模型给出 `0-100` 参与适合度；达到配置阈值、已理解且没有否决原因才放行。
- **`act == "silent"` 优先于分数**：只要模型判定「别插嘴」，即使 `conf` 超过阈值也静默。
  放行还要求 `understood == true`，不能存在背景不足、互聊、结束、已回答等否决原因。
  模型误给高分静默时，互聊/结束/已回答/无贡献最多20分，背景不足最多40分；
  原始分数与原始输出保留用于排查。这是协议纠正，不是统计校准。
- 上下文不足、存在歧义、低于阈值、缺少有效分数或没有回复正文时默认静默。
- 连续碎片消息：同一会话、同一用户每次续发重置安静期，整批只保留一次回复机会；整批另受「碎片批次总等待上限」约束，默认10秒，0不限；明确呼叫免主动冷却。
- 相同消息：在配置窗口内避免重复回复。
- 判定留痕在参与判定实际执行时产生；开启碎片等待的纯文字称呼仍可留痕。
  原生 @ 当前机器人直接放行，不伪造小模型评分；等待设0的明确呼叫、
  被后续分片替代或被其他插件提前拦截的触发也不留参与判定记录。

被硬拦截或暂不回复的消息仍会保留在 AstrBot 已启用的群聊上下文中，供后续回复使用。

插件启动时会把“机器人称呼”同步到 AstrBot 的运行时唤醒前缀，在框架最早的唤醒阶段生效。
同时注册中文/英文逗号和冒号变体，例如配置“龙”后，`龙`、`龙，出来聊聊`、
`龙: 在吗` 都会明确唤醒机器人。同步仅作用于当前进程，不改写 AstrBot 全局配置文件；
插件或服务重载时会根据当前插件配置重新注册。

## 闸门模式

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| `enforce` | 静默判定直接拦截，不生成回复；主模型仍可能用于图片异常兜底分类 | 日常运行（默认） |
| `shadow` | 照常判定并记账，但一律放行 | 换模型/调阈值前跑 2-3 天做对比 |

当前只有以上两种模式。旧 `legacy` / `off` 配置会按 `enforce` 处理。

## 控制台

插件详情页里的 `guard` 页，页面上能改的配置项与设置页对应。多数参数保存后立即生效，
称呼的框架唤醒前缀需要插件重载更新：

- **闸门模式**两种选项（`enforce` / `shadow`）+ 今日运行统计。
- **分数分布与阈值扫描**：最近判定的完整分数直方图（10 档）、当前阈值 → 放行率、
  `P50 / P75 / P90`，以及按目标放行率反推的建议阈值（点一下填入滑块）。
- **参与判断**：阈值、文字模型、文字超时、最短字数。
- **图片与主模型兜底**：视觉模型、视觉超时、兜底开关及超时。
- **上下文与记忆**：判定流水、上下文有效期、记忆检索时限、回复上下文。
- **预算与判定时限**：每群总调用上限、视觉/兜底共享上限、整条判定时限。
- **回复节奏**：碎片等待、主动冷却、相同消息去重、回复机会有效期。
- **称呼、空 @ 与私聊**：机器人称呼、空 @ 方式、固定文案、人格要求和私聊开关。
- **文字试跑**：在配置下方输入消息和机器人上一句查看判定，不发送消息；
  不计插件统计和预算，但实际模型API仍计费。
- **最近判定**：逐条留痕的表格，点「详情」弹窗看该条的完整判定上下文（送给模型的 prompt）
  和模型原话返回，方便人工复核「模型当时看到了什么、为什么这么判」。
- **参数详情与手册**：每项通过标题右侧 `?` 按需展示解释和两个示例；顶部按钮打开可搜索的完整手册。
- **保存浮条**：改动任意配置后，页面底部浮出「有 N 项更改未保存」提示条，可「保存更新」
  或「放弃更改」，保存成功/放弃后自动收起。

判定模型是下拉选择，列表来自 AstrBot 的 provider，**包括插件注册的 provider**——
装了「多 API 模型路由」就会多出一个 `multi_api_router` 选项，下拉里会带出它的上游
（形如 `qwen7b → Qwen/Qwen2.5-7B-Instruct`）。选择路由本身会按优先级选择上游；
选择带「锁定上游」的 `provider::model` 项，则固定使用该具体模型。
图片判定还会校验视觉能力并锁定对应上游。

判定超时默认 3.5 秒：实测热态 p50≈1.3s，但空闲后首个请求会摸到 2.5s 以上，
低于 3s 会把正常消息 fail-closed 静默掉。

最近判定的“判断说明”默认用中文展示模型建议、理解状态、参考流水数和当前消息。
每条记录有当前列表序号；详情中的聊天编号按本次输入顺序排列，显示发送者、年龄、
正文、引用及媒体。`N条参考流水＋1条当前消息` 不额外计入机器人上一句和记忆。
当前消息单列，不保证它比碎片等待期间到达的新消息更晚。规则未调用模型时只显示
候选消息，并明确“未调用模型”，不把未发送的流水算成模型依据。
新日志另存 `chat_data`、`image_summaries`、`image_handoff`；旧日志能解析则恢复分条，
不能解析时保留原文而不猜消息数。原始JSON和输入资料在折叠区保留。

视觉下拉与文字模型下拉分别筛选。已知纯文本的 DeepSeek Flash/Quiet、Qwen3-8B 等
不因宿主默认勾选全部模态而进入视觉列表；后台保存接口和框架配置schema同样校验。
未知型号仍可能依据明确的宿主能力声明，最终可用性取决于实际API；不是所有候选都做过联网探测。

## 数据文件

位于 `data/plugin_data/astrbot_plugin_LivingHello/`：

- `decisions.jsonl`：逐条判定留痕，超过1MiB轮转至时间戳归档，不覆盖旧归档；兼容读取旧`.1`。
- `gate_state.json`：今日计数，跨天自动清零。
- `participation_stats.json`：历史累计（总次数、平均分、放行/静默、分桶）。

## 仅 @ 机器人

在插件配置页的“仅 @机器人时的回复方式”中选择：

| 模式 | 行为 | 适用场景 |
| --- | --- | --- |
| `fixed` | 直接发送“仅 @机器人时的固定文案” | 希望响应稳定、快速且不消耗模型 |
| `persona` | 通过当前会话的模型和人格生成回复 | 希望不同人格以各自语气回应 |

人格模式遵循 AstrBot 的会话人格选择。比如群 A 使用“大小姐”、群 B 使用“猫娘”，两边仅 @
机器人时会分别按各自人格回应。插件不会覆盖会话人格，也不要求为每个人格重复配置 ID。
“仅 @机器人时的人格回复要求”只约束回复简短自然，具体身份和语言风格仍由当前人格决定。

## 配置

碎片重置、合并判断、空 @ 和私聊开关的完整逻辑见 [碎片消息说明](fragments.md)。

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `gate_mode` | `enforce` | 闸门模式，见上一节 |
| `participation_confidence_threshold` | `65` | 最低参与适合度，达到分数还须理解话题并没有静默否决 |
| `classifier_provider_id` | 空 | 判定用的小模型，配置页下拉选择（含「多 API 模型路由」）；留空则跟随会话当前模型（不推荐） |
| `classifier_timeout_seconds` | `3.5` | 判定超时，超时按静默处理（fail-closed） |
| `gate_context_messages` | `8` | 喂给判定模型的群聊流水条数 |
| `gate_context_max_age_seconds` | `300` | 群流水、机器人上一句的最大年龄 |
| `gate_reply_max_age_seconds` | `30` | 自主回复机会有效期，包含等待、判定与生成；配套开启时扣除有效的从绫准备计时 |
| `gate_congling_prepare_compat` | `true` | 从绫准备耗时适配；关闭按原总年龄检查，无有效上报时不扣时 |
| `gate_memory_timeout_seconds` | `1.5` | 按当前完整会话与人格检索背景记忆的超时 |
| `gate_min_length` | `2` | 短文字不经模型直接静默；有可用图片除外；0关闭长度过滤 |
| `gate_hourly_budget` | `60` | 每群每小时判定调用总上限，各层及记忆复判均计入；0不限 |
| `bot_names` | `["助手", "bot"]` | 无 @ 时可明确唤醒机器人的称呼 |
| `empty_mention_mode` | `fixed` | 空 @ 回复方式：固定文案或当前人格 |
| `empty_mention_reply` | `嗯？有事就说。` | `fixed` 模式发送的文案 |
| `empty_mention_persona_prompt` | 内置简短回应要求 | `persona` 模式附加的回复要求 |
| `apply_to_private` | `false` | 私聊是否启用参与判断；与碎片等待、表达及撤回独立 |
| `participation_context_messages` | `12` | 放行后塞给主模型的最近群聊消息数（与判定条数分开配置） |
| `fragment_wait_seconds` | `3` | 同用户每次续发重置的安静期秒数；包含明确呼叫，0关闭 |
| `fragment_max_wait_seconds` | `10` | 该批第一条消息起算的总等待上限；0不限；续发不延长 |
| `fragment_wait_private` | `false` | 私聊是否也等待并合并碎片；与参与过滤开关独立 |
| `proactive_cooldown_seconds` | `8` | 同群自主回复冷却 |
| `duplicate_window_seconds` | `120` | 相同消息回复去重窗口 |
| `vision_provider_id` | 空 | 必须看图时使用的视觉模型；空值按主模型兜底开关处理 |
| `gate_image_cache_ttl_seconds` | `300` | 图片观察缓存秒数，0关闭；范围0–1800；不缓存参与决定 |
| `vision_timeout_seconds` | `6` | 一次多模态判定的等待时限 |
| `gate_main_fallback_enabled` | `true` | 视觉调用异常时用支持图片的会话主模型兜底一次 |
| `gate_main_fallback_timeout_seconds` | `6` | 一次主模型兜底的等待时限 |
| `gate_total_timeout_seconds` | `18` | 整条判定含背景检索；不含碎片等待、回复生成 |
| `gate_vision_hourly_budget` | `20` | 每群视觉及兜底共享调用上限，且仍计总上限；0不限此项 |

默认值来自插件 schema，已保存的实际配置可能不同。控制台显示实际保存值。
例如总预算120次时，一条消息先做文字判定、再看图，会消耗2次总预算；
若随后主模型兜底，再消耗1次，同时视觉共享预算累计消耗2次。
「文字判定超时」只约束一层；「整条判定时限」约束整个判断；
「回复机会有效期」从收消息算到发送，包含等待、判定和生成；
从绫配套开启且当前事件有有效计时上报时，只扣除该次爬楼/补课准备时间。

### 从绫配套

`guard` 页的「回复节奏 → 从绫爬楼配套」保存即生效，并显示已加载从绫的启用状态、
人格钩子顺序。顺序正确不代表旧版已支持计时；有效扣时取决于当前事件上报。
无需从绫时保持默认即可，没有计时则使用原规则；关掉此项也不会关闭从绫的爬楼。

先判定后爬楼、爬楼与补课的独立设置、有效期示例和排查步骤见
[配套插件与功能耦合说明](integrations-and-flow.md)。

## 参与适合度与上下文判断

插件用钉死的判定模型（`classifier_provider_id`）执行一次独立分类，只输出
`{"act","conf","understood","reason","ground"}`；正式人格回复仍走原有会话链路。
分类器不扮演人格，但会看到当前消息发送者、机器人身份、引用对象、媒体缺失提示、
带年龄的近期群流水与新鲜的机器人上一句。`conf` 只表示此刻参与的适合度，
不是模型对静默的信心；`understood` 单独表示是否理解了话题、指代与交流对象。

| 分数 | 定义 |
| --- | --- |
| `0-20` | 群友互聊、原话题已结束、不应打扰、没有贡献 |
| `21-40` | 背景或指代未弄清 |
| `41-60` | 已理解，但参与价值有限或邀请不明确 |
| `61-75` | 已理解，能自然提供具体价值 |
| `76-90` | 明确承接机器人近期发言，并确实需要继续回应 |
| `91-100` | 明确邀请机器人参与，且背景已理解 |

这些是提示词定义，不能视为已校准的正确率。`participation-v5-image-cache` 样本与旧协议分开统计，
分布按实际完成判定的模型区分，视觉及主模型样本不混入文字模型口径。

### 图片参与判断

图片观察新增会话内短缓存，`gate_image_cache_ttl_seconds` 默认300秒，0关闭，最大1800秒。
缓存含义、不缓存“是否回复”；新消息的判定会参考缓存画面，明确结束/互聊仍静默。
只有本插件正常视觉输出可填充缓存，不从其他插件独立回复或描述自动推断。
缓存命中不续期，最多256项，重载清空，完整会话/视觉配置/协议变更后不混用。
原图引用按哈希匹配，签名URL变化视为新引用；本地文件变动会使旧观察失效。
上下文有效期和流水截断仍约束图片选择，缓存TTL较长不代表会使用已经离开话题窗口的图片。

先调用文字小模型；只有输出 `reason=media_unresolved` 或明确的 `need_vision=true`
才升级到 `vision_provider_id` 的多模态小模型。多模态层直接完成同一参与判断，
不再把图片描述转回文字小模型。正常 `silent`、仍看不懂、互聊或结束话题，
均保留静默；只有模型未配置、接口超时/失败或输出协议不完整，才允许当前会话主模型
兜底一次。主模型不支持图片、与失败模型相同、图片不可用或预算耗尽时静默。

图片来自当前消息、引用链和同群近期消息，当前/引用优先、去重后最多3张，
沿用流水条数及300秒默认年龄限制；单个内嵌图片引用最多8MiB。
不扫描聊天文本中的URL，不提前下载，图片地址不写入判定上下文或JSONL。
纯图片消息不被“最短文字”规则丢弃。原生 @ 当前机器人合并后直接放行，
理解能力仍可向主回复附上图片观察；其他唤醒开启碎片等待时合并判定，等待设0时直接放行。
视觉层在同一次判定中返回 `image_summaries`：图片序号、内容摘要、不确定点以及
`needs_original`。摘要连同图片的当前/引用/近期来源作为不可信观察资料附到回复请求。
所有已看图片都有完整摘要、没有不确定点、且明确不需要细节时，优先使用摘要，
移除本次可匹配且已被摘要覆盖的原图；其他插件附带的无关图片不移除。
摘要缺失、超长被截断、图片序号重复/缺漏、有不确定点或需要细节时，仍保留原图。
摘要不足又无法确认回复模型支持图片时静默，不让纯文本模型猜图。
摘要可以支持纯文本主模型回复；它是视觉模型的观察，不能视为已核实事实。

路由会锁定支持图片的上游，找不到锁定型号时绝不退到全部纯文本上游。
宿主配置的 `modalities` / `supports_vision` 优先；没有声明时只识别明确视觉型号，
不能仅凭主流品牌推定支持图片。原生OpenAI适配器在此分类路径使用局部调用包装，
避免宿主在图片报错后悄悄删图重试；不改变共享provider或最终回复流程。

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `vision_provider_id` | 空 | 选择多模态小模型；未配置时按兜底开关处理 |
| `vision_timeout_seconds` | 6秒 | 多模态单次调用时限 |
| `gate_main_fallback_enabled` | true | 视觉异常时用当前会话主模型兜底 |
| `gate_main_fallback_timeout_seconds` | 6秒 | 主模型兜底调用时限 |
| `gate_total_timeout_seconds` | 18秒 | 整条判定链路含记忆补查的时限 |
| `gate_vision_hourly_budget` | 20 | 每群每小时视觉+主模型判定调用共用上限 |

每一层实际调用仍计入 `gate_hourly_budget`，独立视觉预算耗尽不会再花费主模型。
整链路超时、群聊更新和回复机会过期仍静默。文字API异常本身不会触发昂贵的视觉层。
日志 `stage`、`mdl`、`attempts`、`image_count` 可检查实际调用层、模型、原因和耗时。
控制台“试跑一条”目前是文字试跑；图片链路可通过真实平台事件或隔离脚本验证。

阈值保留现有配置，默认65；不再用旧协议的“阈值对应发言比例”推算新策略。
阈值为0也不能越过静默动作、背景不足或停口约束。

`ground=memory` 时，最多按当前完整会话与人格检索3条记忆、复判一次。
身份未知、记忆无结果、超时或预算不足时静默；复判仍需要背景时不继续重试。
`ground=web` 表示问题已理解、需要外部事实，交由主模型已有工具处理；
闸门不自动搜索网页，主模型不能核实时应返回 `[[ASTRBOT_NO_REPLY]]`。

结束原话题不代表永久禁言；随后出现新的明确问题或澄清误会，需要重新判断。
群聊默认不因水位机制顶替旧答；`watermark_scope=all` 时按配置窗口执行。
私聊默认窗口内顶替，撤回和过期另外检查，需要结合真实人工标注评估。
原生 @、叫名字免主动冷却；原生 @ 当前机器人合并后直接放行。
纯文字称呼开启碎片等待后仍需参与判断，等待设0时直接放行。

例如机器人刚说“学不来，太损了”，紧接着用户说“损人也是你的必修课”，属于明显承接
机器人上一句，预期约 `80-90` 分；默认阈值 `65` 应当放行。

`enforce` 模式下低分会在 `on_llm_request` 里直接 `event.stop_event()`，主模型**根本不会被调用**，
省下的是生成侧的钱（实测旧行为下被静默的消息每条都完整生成过一遍，约 ¥2.6/天、占全站 17%）。
旧 `legacy` 已不作为可选模式，存量值归一为 `enforce`。

插件会把实际判定累计到 `data/plugin_data/astrbot_plugin_LivingHello/participation_stats.json`，
并在 INFO 日志记录每次分数。发送 `/智能过滤统计` 可查看当前阈值、实际平均分、放行次数和静默次数。

### 为什么不用“被拦分数中位数”定阈值

老版本记录“最近 1000 条被终止评分的中位数”，看上去像个调节参考，数学上却站不住：

- 那批样本是**右删失**的——凡是 ≥ 阈值的分数根本不会被记进来，样本里只有尾巴。
- 于是中位数必然落在阈值下方，而且**阈值一动它就跟着动**。阈值 65 时它显示 30，
  你把阈值调到 30，它就变成 20 出头。等于用尾巴估计整体，永远得不到“该定多少”。
- 更糟的是它会给人“阈值很合理”的错觉：分数永远低于阈值，看起来像拦得没错。

正确的做法是看**全分布**：所有判定的分数（不论放行还是拦下）画成直方图，再按 0~100
每 5 分一档算“阈值设在这里会放行百分之多少”。这就是控制台里「分数分布与阈值扫描」那一块：
直方图 + 通过率曲线 + `P50/P75/P90` + 按目标放行率反推的建议阈值。

那个中位数指标**已经删除**（含 `participation_blocked_median_reference` 配置项、
`blocked_scores`/`blocked_median` 统计字段），不再保留诊断项。定阈值只看全分布。

### 换判定模型要重新标定阈值

分数尺度是跟着判定模型走的。实测同一句话（“助手你觉得这个新番好看吗”）：

| 判定模型 | 返回 |
| --- | --- |
| `deepseek/deepseek-flash` | `{"act":"reply","conf":78}` |
| `multi_api_router`（7B 上游） | `{"act":"silent","conf":41}` |

差 37 分。所以：

- 判定留痕记录完整 `provider::model` 与评分协议，分布统计只算当前模型和当前协议；
  曲线还检查 `act`、`understood`、否决原因，不能把所有高分都算成放行。
- 换模型后先做隔离评估；`shadow` 只记录不拦截，并不保证机器人保持静默。

### 判定样本从哪来

`decisions.jsonl` 超过1MiB轮转至时间戳归档；插件启动时跨文件恢复最近600条有效记录，
所以重启不会把分布清零。升级前的旧日志没有 `mdl` 字段，无法判断是哪把尺子量的，
会被归为“未知”并排除在当前口径之外——控制台会明确写出被排除了多少条。

## 推荐设置

1. 开启 AstrBot“群聊消息记录注入上下文”。
2. 开启 AstrBot“主动回复”，按需要设置原有回复概率。
3. 安装并启用本插件。
4. 在插件配置中选择空 @ 回复方式和私聊作用范围，并调整参与置信度、称呼、上下文条数、冷却、碎片等待和去重窗口。

## 判定日志为什么是空的（排查思路）

控制台「最近判定」偶尔一条都没有，多半不是插件坏了，而是**那条消息根本没走到判定这一步**。
判定钩子挂在 `on_llm_request` 上，只在「消息真正发起主模型请求」时才触发。以下情况**不会**产生判定记录：

- **原生 @ 当前机器人**：合并后直接放行，不走参与判定或伪造评分；纯文字称呼开启碎片等待时仍判断并留日志。等待设0的明确呼叫、整批仍为空 @ 的固定/人格快捷回应也不走参与判定。
- **被其它插件提前拦截**：如果某个插件在更早的阶段 `stop_event()` 了（比如装了 `congling`，
  它的「长夜/夜间休眠」会在凌晨把普通群消息拦下、只有点名才理人），消息到不了判定钩子，
  自然没有日志。判断方法：AstrBot 日志里能看到
  `Stage ProcessStage stopped event propagation.` 却没有 `guard_llm_request` 的调用。
- **消息没到机器人**：OneBot 连接断、群消息被平台侧过滤等，这类连插件的第一个钩子都不会进。

排查步骤：

1. 先在控制台「试跑一条」里手动喂一条消息，看判定引擎和模型是否正常——能出分数就说明插件本身没问题。
2. 把 AstrBot 的 `log_level` 调到 `DEBUG`（`cmd_config.json`，注意该文件带 BOM，要用 `utf-8-sig` 读），
   重启后发一条消息，看日志里有没有 `apply_hard_group_rules`（第一个钩子）和 `guard_llm_request`（判定钩子）。
   只有前者没有后者，就是消息在中间被别的插件拦了。
3. 正常情况（白天、普通群消息、没 @、`proactive_group_judge` 未设为 `off`、没被其它插件拦）下，判定日志会实时出现。

> 提示：AstrBot 的插件加载日志在 `log_level=WARNING` 下看不到（INFO 被吞），
> 排查时先切到 `DEBUG` 再看。

## 限制

“别人之间的私聊式对话”和“明显接续上一条消息”属于语义判断。插件会提供近期上下文并要求模型仅在高置信度时放行；模型不遵循输出协议时也会默认静默。仅 @ 其他用户的规则不依赖模型，属于确定性硬过滤。
