# 多图两张批次

2026-11-17已在生产服务器以同组9张图片进行首组真实对照：每批2张耗时17.2493秒，每批4张耗时12.0595秒。但四张批次把独立的青蛙和猫图合并为同一画面的上下部分，后续卡车及人物的图片编号也错位。模型正常返回且未触及输出上限，离线路径通过不能替代逐图质量验收。

四张方案未通过质量验收。用户要求恢复每批2张后，本地实现已恢复为与线上相同的两张批次，两张方案已完成3轮测试：1轮完整、2轮部分完成，共3批超时。成功摘要中未发现四张首组的混图及编号漂移；但现有12秒单批预算下，完整读取稳定性未通过本次小样本验证。超时请求即使在上游完成并产生usage，也不能算插件已经取得图片摘要。

`input/guard_understanding.py` 的 `_enrich_images()` 按原始顺序每2张组成一批，最后一批可以只有1张。每批的观察按原图编号排列，完成顺序不会改变最终摘要顺序。

所有消息共用2个视觉请求并发槽。单轮最多读取12张，合并分片共用最多6次调用预算。12张单条消息调用6次；9张调用5次。每张图片分别走已有图片预算处理。

每批仍限制512输出token、12秒模型请求时间，并只尝试一次。输入理解总时限仍读取已有配置。某批失败时保留其他成功批次的观察，并标记未读图片；总时间耗尽时再取消剩余任务。

不引入OCR。图片预算和原有压缩逻辑继续生效；准备图片在同样的两个并发槽中逐张处理。

`tests/test_multi_image_budget.py` 验证12张调用6次、最多2路并发、7张按2/2/2/1分批的顺序和编号、部分失败、超时取消及跨消息共享调用预算。

真实测速在同一服务器、同一Provider、同一组原图和相同参数下执行；记录整个图片理解阶段、各批耗时、成功率、逐图覆盖及实测token。四张首组只作为已拒绝的历史对照。两张方案只有1轮完整读取，不能把失败轮的结束耗时混算成完整读取的中位数，不推算p95或长期提速比例。
