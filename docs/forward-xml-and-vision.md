修复日期：2026-11-17。

## 问题与根因

| 触发情况 | 修复前 | 根因与修复 |
| --- | --- | --- |
| 路由声明 HY4 支持图片，配置页可以选择 | 运行时仍可能拒绝，无法取得图片观察 | 配置页采信 `api_type`，运行时却按型号或缺失的 modalities 再检查；统一能力判据并在直连时保留声明 |
| 外层转发包含 XML 聊天记录卡片 | 只按普通卡片读取预览，无法识别内部转发 | 将 `viewMultiMsg/serviceID=35` 识别为转发，复用原遍历链路与回拉预算 |
| XML 没有资源 ID，或回拉结果为空 | 无法可靠区分预览与已展开正文 | 明确标注内部未展开，不使用文件名伪造资源 ID |

## 视觉模型

配置页与运行时共用视觉 API 类型集合。路由上游明确声明
`api_type=image_to_text` 或 `multimodal` 时，可被选作视觉模型；声明为
`chat` 或其它类型时，不进入视觉候选。原生 Provider 的能力声明及型号判断保持原有规则。

图片理解先锁定符合能力要求的上游，再直接调用该 client。直连时保留同一份
`api_type`，避免 HY4 等型号在第二次检查中被拒绝。OpenAI client 继续使用严格
视觉适配器，报错不会删掉图片重试。

没有修改所选 Provider、上游配置、展开开关或层数/条数配置。

## XML 嵌套聊天记录

输入解析识别 `<msg>` 的 `action=viewMultiMsg` 或 `serviceID=35`。
有 `m_resid`（兼容 `resid`）时，通过 OneBot `get_forward_msg` 回拉内部消息，
按普通合并转发继续遍历文字、图片和下一层转发。

XML 和普通 Forward 共用同一事件的去重、来源名单、层数、条数、8 次平台回拉及
10 秒回拉总预算。外层也计入层数：配置为 1 时，内部转发会明确标记达到层数上限。

`m_fileName` 是文件标识，不作为回拉资源 ID。资源 ID 缺失或平台回拉失败时，
明确说明内部未展开；若允许卡片解析且没有启用黑名单，可附标题/摘要，并标注
“仅卡片预览，不代表已读取内部消息”。启用黑名单时，隐藏无法核验作者的预览。
空返回也会明确标记未展开。

普通 XML 卡片保持原有处理。畸形 XML、超过 60000 字符或含 DTD/实体声明的 XML
不会触发转发回拉，不加载 XML 外部资源。

## 使用与排查

1. 在「内容理解」确认展开开关、最大层数和最多展开条数。外层也计入层数，
   最大层数为1时不展开内部的下一层转发；升级不会自动提高现有配置。
2. 检查 XML 是否带 `m_resid/resid`。缺失时只能说明内部未展开，不能凭文件名
   或预览恢复正文。不要把“识别成功”理解成“所有聊天记录都能恢复”。
3. 有资源 ID 但平台回拉失败时，检查平台的 `get_forward_msg` 支持情况；
   来源名单、重复 ID 或回拉预算也可能阻止展开。
4. 图片模型在路由侧应声明 `image_to_text/multimodal`；原生 Provider 沿用其
   能力配置。候选可选说明配置判断通过，实际图片输入能力仍取决于上游。
