# 主模型失败兜底

`reply_fallback_enabled` 默认关闭。在“回复与私聊 → 断线恢复”打开“兜底回复”，填写“异常提醒管理员 QQ”并保存。QQ 留空使用 AstrBot 全局管理员。本开关独立生效，不要求同时开启文字判定断线恢复。

仅接入已通过本插件请求闸门的 AstrBot 本地 ToolLoop Agent。未开启私聊过滤的私聊不接入；外部 Agent、接口不兼容或容量已满时保留宿主流程，并在请求追踪标记未接入原因。开关关闭后，正在等待的重试最多一秒内结束；插件重载会取消等待和本插件接入的模型请求，恢复 runner 方法。

## 调用顺序

1. 首次主模型调用失败，最多再调用 5 次。异常、错误角色和空结果都属于失败；明确不回复标记和工具调用结果不属于失败。
2. 重试间隔为 1、2、4、8、16 秒，每次增加 0～0.25 秒随机抖动。可使用宿主已有回退模型，按主模型及回退模型顺序轮换。
3. 首次加 5 次重试都失败后，先尝试向管理员 QQ 私聊，再等待 60 秒。
4. 做最后一次模型调用，仍失败就结束并保留异常记录。一个持续失败的模型步骤最多 7 次调用，不无限循环。

每次模型调用上限 60 秒；同一事件从接入起最多 540 秒、最多 5 次普通重试加 1 次延后尝试。工具后续步骤共享剩余重试预算；新步骤的正常首轮调用不算重试，因此完整工具流程的正常调用总数可能超过 7 次。最多同时接入 16 个 runner，超出容量不排队。

这里的次数是插件调用 Provider 的次数。接管期间将宿主 `request_max_retries` 设置为 1，并替换该 runner 的空结果重试层，防止常规重试相乘。Provider 自身的模型路由、换 Key 或协议修复仍可能执行额外 HTTP 请求，不能将“7 次 Provider 调用”当成所有供应商 SDK 的网络请求次数保证。

## 保护条件

重试复用当前 runner 和已保存的工具结果，只调用失败的模型边界，不重新执行 Agent、闸门、记忆准备或工具。成功后由原生结果钩子、排版、分段与平台发送流程继续处理。

任何流式片段已经输出，就不重试该次失败；已经尝试发送、发送结果未知或发送失败也不重放。每次调用前和等待期间复核开关、撤回、名单、事件停止、Agent 取消和有效期。已放行的群聊首次调用及工具后的正常调用不检查重试专用上下文水位；只有失败后的重试及等待期间复核新消息水位。保护取消调用当前 runner 的停止接口，终态只记录一次；不支持该接口时不接管。最后发送仍接受既有 LivingHello 和配套插件复核。

普通回复有效期默认 30 秒。只扣除本功能实测的失败调用、提醒和退避耗时，让一分钟后的调用有机会执行；成功生成耗时仍受原期限限制，新消息与权限保护不因等待而失效。兜底总期限和健康监测超时独立限制总等待；健康监测默认 900 秒，手动设得较短会提前结束等待，准备耗时也占用健康监测期限。

## 提醒与留痕

管理员通知仅限 QQ/OneBot 私聊，附当前消息的安全摘录和请求编号，不转发上游异常原文。提醒复用 `outage_notify_admin_qq` 和 `outage_notify_interval_minutes`，默认最小间隔 10 分钟，限频额度持久化。无有效 QQ、平台不支持、限频或通知未知时，保留通知状态，仍执行有界的最后尝试；通知结果未知不自动重发。

各次调用和等待写入请求追踪。最终成功以有效正文的实际投递为准；最终失败进入“最近判断”，保留原判定证据。正常静默、冷却、重复消息和明确不回复不作为模型故障。JSON、单引号及普通键值中的凭据在管理员摘录和新建异常摘要中隐藏；既有判定正文和历史日志不由本功能改写。

## 验证与限制

`tests/test_retry_context_fix.py` 补充首次生成、新工具步骤、单次取消终态和保护条件反例。`tests/test_reply_fallback.py` 覆盖次数、通知先后、60 秒等待、快速恢复、流式中断、未知发送、工具结果保留、取消、超时、重载、共享预算、静默及摘录落盘。设置 `ASTRBOT_HOST_SOURCE` 可运行实际宿主调度器、runner 请求方法和完整 `step()` 钩子绑定路径；宿主依赖和平台仍为替身，不触发付费 API。

已验证本机 AstrBot 4.29.3 的方法接口。当前依赖宿主内部 runner 方法及当前栈定位，升级宿主后应重新执行该检查；不兼容时不接管。浏览器检查使用合成配置接口，无生产修改或真实 QQ 私聊。
